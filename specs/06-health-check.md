## 1. Goal
The user can see, in one place, anything on the phone that would stop reminders firing or nagging, and can jump to the right system setting to fix it. A yellow warning on the menu or home, copied from Due's sidebar button, appears when something is actually wrong. A one-minute test alarm proves delivery on this device.

## 3. Scope

### A. What the user sees

Due is iOS, so it has no Android permission checker. The pattern to copy is the yellow warning triangle on the sidebar / menu button (`due-0.jpg`, `due-1.jpg`, `due-2.jpg`, `due-3.jpg`) and a concrete warning in the sidebar itself. On Tim's iPad the visible sidebar warning is "Reminders Not Backed Up" under Sync (`email2-image4.jpg`). Backup is a later spec. Do uses the same badge and menu pattern for Android delivery health, which Due does not need.

**Menu button.** Add a menu control on the reminder list top bar, in the Due sidebar-button position (leading, next to the title). Tapping it opens a compact menu. Include a "Health check" row that opens the health screen. When any Blocking or Warning item is unhealthy, a yellow warning mark sits on the menu button, as in the Due shots. A Check-only item (Samsung guidance with no detected fault) does not light the badge, so the mark does not sit there permanently on a Galaxy. After a late fire, the badge comes on even if every permission API still looks fine.

**Existing list banners stay.** Spec 1 already shows "Notifications are off, so nothing will alert." (`banner_notifications`) and "Reminders may be late. Allow Alarms & reminders" (`banner_exact_alarm`). Keep both, with their existing Fix buttons. The badge and health screen sit on top of them, they do not replace them.

**Settings.** The Spec 5 "Full-screen alerts" and "Do Not Disturb access" status rows stay. Add a "Health check" row in that test-harness Settings section that opens the same health screen. Do not duplicate every health item in Settings.

**Health screen.** Title "Health check". A short lead line, assumed: "These checks look for anything that would stop reminders firing or nagging." Then one row per item below, in this order. Each row has a status, a title, a one-line plain explanation, and a Fix button when the item is not OK. Fix deep-links to the matching system screen and returns to this screen on back; the check re-runs on resume so the row can flip to OK without a manual refresh. A "Test alarm in 1 minute" button sits at the bottom (section 3C).

Statuses:

- **OK:** nothing to fix. No Fix button.
- **Warning:** reminders may be late, silent, or fall back (exact alarm missing, battery still optimised, a channel muted, full-screen or DND missing, a late fire, a missed boot receipt, Restricted or Never standby).
- **Blocked:** this setting can stop alerts outright (notifications off, a reminders channel blocked, background restricted, or the boot receiver component disabled).
- **Check:** guidance the app cannot prove from a public API. Used for the Samsung Sleeping / Deep sleeping row. No badge on its own.

Australian English on every user-facing string. Do not invent Due copy for this screen.

### B. The checks

Evaluate all of these on every run of the checker (section 3C). Unit-test the evaluator from plain inputs, so the status rules below are not only on a device.

**1. Notification permission (`POST_NOTIFICATIONS`).** Use `AlarmPermissions.canPostNotifications()` (already true below API 33, and a runtime check on API 33+). Blocked when false. Explanation: "Notifications are off, so nothing will alert." Fix: `Settings.ACTION_APP_NOTIFICATION_SETTINGS` for this package, the same destination as the existing banner button.

**2. Channel importance and muted channels.** Inspect `reminders`, `reminders_critical` and `reminders_prominent` (`ReminderNotifier` channel IDs). A channel is unhealthy if it is missing when it should have been created, `importance` is `IMPORTANCE_NONE`, or `channel.isBlocked` is true (API 28+). One unhealthy channel is enough. Blocked, because a muted Reminders channel is how a user silences every nag without turning the app permission off. Explanation names the unhealthy channel, for example "The Reminders channel is muted, so alerts will not make a sound or appear." Fix: `Settings.ACTION_CHANNEL_NOTIFICATION_SETTINGS` for the first unhealthy channel, with `EXTRA_APP_PACKAGE` and `EXTRA_CHANNEL_ID`; if that intent does not resolve, fall back to `ACTION_APP_NOTIFICATION_SETTINGS`. The `reminders_summary` channel is meant to be `IMPORTANCE_LOW` and silent; never treat that as a fault.

**3. Exact alarm (`canScheduleExactAlarms`, both build flavours).** Use `AlarmPermissions.canScheduleExact()`. On API 30 and below, this is OK (no special permission). On API 31+, Warning when false: the scheduler already falls back to `setAndAllowWhileIdle()`, which is late-OK and at most once per nine minutes in Doze (Spec 1). The status text must say which flavour the running build is (`ExactAlarmPolicy` / `exactAlarmMode`): "USE" or "SCHEDULE". On a default USE build on API 33+, `USE_EXACT_ALARM` is granted at install and the user cannot revoke it, so this row should be OK unless the platform says otherwise. On API 31-32 the USE build still depends on `SCHEDULE_EXACT_ALARM` with `maxSdkVersion="32"`, and on a SCHEDULE build the grant is always user-controlled (Spec 1). Explanation when missing: "Alarms & reminders is off, so reminders may be late." Fix: `Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM` for this package, the same destination as the existing banner. Do not change the flavour or the manifest rules in this PR.

**4. Full-screen intent (`canUseFullScreenIntent`, Android 14+).** Use `AlertPermissions.canUseFullScreenIntent()` (already returns true below API 34). Warning when false. This does not stop Standard or Critical, and Spec 5 already falls back Prominent to a Critical-style notification. Explanation: "Full-screen alerts are off, so Prominent reminders fall back to a Critical-style notification." Fix: `AlertPermissions.fullScreenSettings()`, which is already `ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` on API 34+. Always show the row, so the user can grant it before choosing Prominent. Play pre-grant and the Console declaration stay with Tim, as in Spec 5.

**5. Do Not Disturb access for Critical (Spec 5).** Use `AlertPermissions.hasDndAccess()`. Warning when false. Critical still posts, but may be silent under DND (Spec 5 call 8). Explanation: "Do Not Disturb access is off, so Critical reminders may be silent when Do Not Disturb is on." Fix: `AlertPermissions.dndSettings()` (`ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS`). Always show the row.

**6. Battery optimisation (`isIgnoringBatteryOptimizations`).** Warning when `PowerManager.isIgnoringBatteryOptimizations(packageName)` is false. Explanation: "Battery optimisation is still on for Do. On some phones that can stop nags after a few hours." The "few hours" wording follows nag's FAQ (s. 5.1), not a Due source. Fix: `Settings.ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`, which opens the system exemption list. The user has to find Do in that list. Do not use `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, and do not add `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` to the manifest.

Why the safer link: Google Play "prohibit[s] apps from requesting direct exemption from Power Management features, Doze and App Standby, in Android 6.0 and above unless the core function of the app is adversely affected" (Doze page, `src/doze.html`). The same page says most apps should use `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`, and only apps with an acceptable use case may use the one-tap `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` intent. The official acceptable-use table (live Doze page, 22 Oct 2026) lists instant messaging, calling, enterprise VoIP, safety, task automation, and peripheral companion apps. It does not list reminder, alarm, or calendar apps. Device and Network Abuse also forbids bypassing system power management unless the app is eligible (`src/answer_16559646.txt`). Do already uses `setAlarmClock()`, which "continue[s] to fire normally" in Doze, so stock Android does not clearly meet the "core function is adversely affected" test. OEM killers are real, and an exemption still helps there, but that is not an listed acceptable use case for the direct request. Recommended default, therefore: the app does not qualify for the one-tap request in this PR. Opening the settings list is the documented path for everyone else.

**7. Background restriction (`isBackgroundRestricted`).** API 28+. Blocked when `ActivityManager.isBackgroundRestricted` is true (the user has set Battery usage to Restricted). Explanation: "Background activity is restricted, so reminders may not fire once Do is in the background." Fix: `Settings.ACTION_APPLICATION_DETAILS_SETTINGS` for this package. From there the user opens Battery and chooses Unrestricted, or the equivalent label on that device. There is no public intent that opens the Restricted toggle directly; do not invent one. Below API 28, skip the row or treat it as OK.

**8. Samsung Sleeping apps / Deep sleeping apps.** Show this row only when `Build.MANUFACTURER` or `Build.BRAND` is `samsung`, case-insensitive. Don't Kill My App rates Samsung at its worst level and describes Sleeping apps, Deep sleeping apps, Never sleeping apps, and "Put unused apps to sleep" (https://dontkillmyapp.com/samsung; `src/dkma.txt`). Samsung's own steps are Settings, then Battery and device care, then Battery, then Background usage limits (ANS10003442). Deep sleeping apps "will never run in the background" and only work when opened, which would stop nags. Don't Kill My App's developer section says "No known solution on dev end", and there is no public Android API that reports whether Do is on those lists. Status is therefore Check, not a guessed OK or Blocked. Explanation: "On Samsung, Sleeping apps or Deep sleeping apps can stop reminders. Check that Do is not on those lists, add it to Never sleeping apps, and turn off Put unused apps to sleep." Fix: if a system or Device Care intent that opens Battery or Background usage limits resolves on this device (`resolveActivity` non-null), use it. Do not hard-require an undocumented action. If nothing resolves, open `Settings.ACTION_SETTINGS` (or app details as a last resort) and keep the path in the row so the user can walk it. Cite Don't Kill My App in the health screen with a "Learn more" link to https://dontkillmyapp.com/samsung. Other OEM guides (Xiaomi, OnePlus, Huawei, and the rest in s. 5.1) are out of this PR.

**9. App standby bucket.** Read this app's own bucket with `UsageStatsManager.getAppStandbyBucket()`. That call does not need `PACKAGE_USAGE_STATS` when it is for the calling app. Warning when the bucket is `STANDBY_BUCKET_RESTRICTED` or `STANDBY_BUCKET_NEVER`. Active, Working set, Frequent and Rare are OK; still include the bucket name in `DUMP_HEALTH`. Explanation when warning: "Android has classed Do as rarely used, which can limit background work." Fix: `Settings.ACTION_APPLICATION_DETAILS_SETTINGS`. The user cannot set the bucket directly; using the app and turning off battery optimisation are the practical fixes. Assumed threshold: Restricted and Never only. Rare is shown in the dump but does not warn, because `setAlarmClock()` is documented to fire in Doze and the product has no evidence that Rare alone stops nags.

**10. Boot receiver and direct boot state.** `RescheduleReceiver` is already `directBootAware` and listens for `LOCKED_BOOT_COMPLETED` and `BOOT_COMPLETED` (and the other Spec 1 reschedule actions). This PR records, in device-protected storage so locked boot can write, the timestamp and boot count of the last `LOCKED_BOOT_COMPLETED` and the last `BOOT_COMPLETED` the receiver actually handled. Use `Settings.Global.BOOT_COUNT` when it is readable, and also store `SystemClock.elapsedRealtime()` at receipt so a reboot can be distinguished from a later app start.

- If `PackageManager.getComponentEnabledSetting` for `RescheduleReceiver` is disabled, Blocked. Explanation: "The boot receiver is disabled, so reminders will not be restored after a restart." Fix: try re-enabling our own component, then re-check; if it is still disabled, open app details.
- After a reboot, once the user is unlocked: if `BOOT_COMPLETED` has not been recorded for this boot, Warning. "Do did not hear the unlock-after-restart event, so some reminders may not have been restored."
- After a reboot, if there were mirror entries that needed a pre-unlock schedule and `LOCKED_BOOT_COMPLETED` was not recorded for this boot, Warning. "Do did not hear the restart event before unlock, so a reminder due before you unlock may have been missed."
- After unlock, if Room has active reminders and the mirror has no matching entries, Warning. "Some reminders are missing from the restart copy, so they may not fire before the first unlock."
- On a fresh install with no reboot yet, this row is OK. Current lock state (`UserUnlock.isUnlocked()`) is included in `DUMP_HEALTH` but is not a fault.

Fix for the missed-receipt and missing-mirror cases: a "Restore alarms now" action on the row (not a system settings page) that calls `Scheduler.rescheduleAll()` when unlocked, or `rescheduleFromMirror()` when not, then re-checks. Also offer app details, because an OEM autostart setting may be why the broadcast never arrived, and there is no reliable public deep link for every OEM autostart screen.

### C. When the check runs, late fires, and the test alarm

**When it runs.** Run the evaluator on process start (`AppContainer.start`, alongside the existing reschedule), on every `MainActivity` resume, when `RescheduleReceiver` handles `LOCKED_BOOT_COMPLETED` or `BOOT_COMPLETED` (record the receipt first), and when a fire is detected late. Persist the last result so the badge is correct on first composition, then refresh. Do not auto-navigate to the health screen, and do not show a new dialog on every resume.

**Late fire.** `AlarmReceiver` already logs `DoAlarm fire id=<id> scheduled=<ms> actual=<ms>` (Spec 1). This PR also compares those numbers. If `actual - scheduled` is greater than 60,000 ms, the fire is late: that is the Spec 1 real-phone on-time tolerance and the brief's "within one minute" metric. A fire before the scheduled time is not a health item (it is a scheduler bug and stays a test fail). On a late fire, log `DoAlarm health-late id=<id> scheduled=<ms> actual=<ms> lagMs=<ms>` (no title), persist the last late fire in device-protected storage, and set a Warning item "A reminder fired late" with the lag in plain words, for example "A reminder fired 3 minutes late." On a Samsung device, that explanation also points at the Sleeping apps steps. The Warning lights the badge. It clears when a later test alarm, or a later ordinary fire, lands within tolerance, or when the user dismisses it from the health row (a "Clear" action, assumed). The 60 second threshold is a Gareth call, not a Due fact.

**Test alarm in 1 minute.** The health screen button schedules a Standard reminder, title "Health check test", nag off, due in 60 seconds, through the normal `Scheduler.add` / `setAlarmClock()` path. It is not Critical or Prominent, and it does not prompt for new permissions. When it fires, log `DoAlarm health-test id=<id> scheduled=<ms> actual=<ms>`, mark it done (so it does not sit on the list), and update the health screen: OK if the fire is 0 to 60 seconds after scheduled and not early, Warning otherwise. If the user leaves the health screen, the test still runs. A second tap before the test has fired does not stack another test; it keeps the one already armed. Debug builds also expose this through `.debug.TEST_HEALTH`.

### D. Debug hooks, tests and the phone runner

Debug-only, same exported `DebugReceiver` as Specs 1 to 5, not in release:

- `com.evansappstudio.doapp.debug.DUMP_HEALTH` logs one line, `DoAlarm health ...`, with a stable key=value set covering every item: `notif`, `channels`, `exact` (and the flavour), `fsi`, `dnd`, `battery`, `bgRestrict`, `samsung` (`NA` on a non-Samsung device, else `CHECK`), `standby` (name and numeric bucket), `boot`, `unlocked`, `lastLate` (`none` or `lagMs`), `test` (`none` or the last test result). Status words are `OK`, `WARN`, `BLOCKED`, `CHECK`, `NA`.
- `com.evansappstudio.doapp.debug.TEST_HEALTH` arms the one-minute test alarm and logs `DoAlarm health-test scheduled=<ms>` immediately, then the fire line above when it goes off.
- `com.evansappstudio.doapp.debug.NOTE_LATE` with `--el lagMs <ms>` records a synthetic late fire (or clears it when `lagMs` is 0 or missing) so the badge and `lastLate` can be tested without moving the clock. Log `DoAlarm health-late synthetic lagMs=<ms>`.

The PR ships unit tests for the evaluator: every status rule in section 3B, the 60,000 ms late boundary (60,000 exact is not late; 60,001 is), Samsung row presence, summary-channel exclusion, and that the battery Fix intent action is `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`. `checkAlarmManifests` (or a sibling check in that task) also asserts that no variant's merged manifest contains `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, and that the release build still has no debug receiver.

The PR also ships `qa/run-spec-06.ps1`, a PowerShell 5.1 phone runner in the style of `qa/run-spec-05.ps1`. Required:

- UTF-8 BOM, `#Requires -Version 5.1`, `[CmdletBinding()]` on the script and on every helper, named parameters only, `-DryRun`, `-Only AT-02,AT-05`, `-Ref`.
- Clone or fetch into `C:\Users\tdrev\do-qa\repo`, build the default USE debug APK, install on the S24+ (`R5CXC0FWWVN`), evidence under `C:\Users\tdrev\do-qa\qa-evidence\Do-spec06-<stamp>\`, results at `C:\Users\tdrev\do-qa\results-spec-06.md`.
- Due times and dumps that include a time are compared truncated to the local minute. Fire tolerance stays 0 to 60 s on the phone, and a fire before the scheduled time is always a FAIL.
- Always restore phone state in a `finally` block, including any notification permission, channel importance, battery or background-restriction appops, standby bucket, leftover `T_s6_*` or "Health check test" reminders (Repeat Off, then Mark Done), and the scheduled DND rule if the run snoozed it (`OVERRIDE_DEACTIVATE` on Sleeping / `EVERY_NIGHT_DEFAULT_RULE`, then re-activate the rule; restoring only `zen_mode` is not enough). The restore is logged.
- Never set a PIN, never factory-reset, never change the clock or time zone, never turn on silent mode as a leftover. Never use force-stop; if `am kill` leaves the process running, the row is RECORD, not FAIL.

## 6. Risks
- **`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`.** Declaring it, or firing the one-tap dialog, is a Device and Network Abuse / power-management review risk. The official acceptable-use table does not name reminder apps. This PR stays on the settings-list intent on purpose. If Tim later wants the one-tap dialog, that is a Play-declaration decision for him, not a silent follow-up in this PR.
- **`USE_EXACT_ALARM` and `USE_FULL_SCREEN_INTENT` reviews** are unchanged from Specs 1 and 5. A reminder app is still not explicitly listed for either pre-grant. This PR does not add a declaration or change the flavour.
- **Samsung Sleeping apps cannot be detected.** A Galaxy can look healthy in every public API and still drop nags after a few days ("Put unused apps to sleep", Don't Kill My App). The late-fire Warning is the backstop. Emulator passes will not catch this; the S24+ run and Tim's later natural use will.
- **Fix deep links vary by OEM and One UI version.** An intent that works on a Pixel may land in the wrong Samsung screen, or nowhere. Every Fix must survive a missing `resolveActivity` and fall back to app details or system Settings, with the path still written on the row.
- **Battery optimisation Warning may always be on** if Tim has never exempted Do. That is a real Warning, and it will light the badge on first install of this PR. Mark should record the starting state so we do not treat a pre-existing setting as a product fail.
- **Direct boot receipts** depend on the OEM actually sending `LOCKED_BOOT_COMPLETED`. A missing locked-boot receipt is a Warning and a log, not an automatic product fail when alarms are restored after unlock (AT-15).
